# Java expert

Modern Java teams can use a new JDK as a build host without shipping new bytecode, APIs, or syntax.
The boundary is Java 11: enforce it in the compiler, verify it against the Java 11 API, and execute tests
on a real Java 11 runtime rather than trusting a version flag.

**Work in this order.** Fix the runtime contract, make the build prove it, choose Java 11-safe idioms,
then optimize measured bottlenecks. A green build on JDK 21 proves little unless all three compatibility
dimensions—class-file version, referenced APIs, and runtime behavior—are independently checked.

## Cross-version compatibility

### Rules

1. **Compile with `maven.compiler.release=11` because `source` and `target` constrain syntax and bytecode but still expose the build JDK's newer APIs.**
   `source=11,target=11` on JDK 21 can compile `Stream.toList()` and emit Java 11 bytecode that fails at runtime.
   `release=11` selects Java 11 language rules, class-file version 55, and the documented Java 11 API surface.
   Use Maven Compiler Plugin 3.13+ and delete parallel `source` and `target` properties.
   Fail builds running below the chosen build JDK with Maven Enforcer; do not silently change semantics by host.

2. **Test on a real JDK 11 because `--release 11` cannot reproduce the Java 11 VM, providers, locale data, garbage collectors, or reflection behavior.**
   Configure Maven Toolchains and Surefire's `jdkToolchain` so forked test JVMs resolve version 11.
   Keep a JDK 21+ job too; the support matrix is the oldest runtime and the development runtime.
   Print `java.runtime.version` in test diagnostics so a misconfigured runner cannot masquerade as coverage.
   Treat “toolchain 11 not found” as infrastructure failure, never as permission to run tests on the host JDK.

3. **Add an API-signature check because compiler settings can be bypassed by generated bytecode, misconfigured modules, or alternate build paths.**
   Run Animal Sniffer with `org.codehaus.mojo.signature:java11:1.0` during `verify`.
   Keep `ignoreDependencies=false` when application code may expose dependency types in public signatures.
   Investigate every undefined reference; exclusions convert a compatibility guarantee into an undocumented exception.
   Use `jdeps --multi-release 11 --recursive target/*.jar` as a diagnostic, not as the sole build gate.

4. **Compare published APIs with `japicmp` because runtime compatibility includes consumers compiled against the previous artifact, not only JDK API usage.**
   Compare the current JAR with the last released JAR in CI for libraries and shared platform modules.
   Fail on removed public methods, narrowed visibility, incompatible return types, and newly abstract interface methods.
   Review generic-signature changes even when erasure is stable; source compatibility can break without binary failure.
   Animal Sniffer detects references to unavailable JDK APIs; japicmp detects leaks and breaks in your own API.

5. **Use a multi-release JAR only for isolated runtime-specific implementations because versioned classes multiply test and packaging paths.**
   Put the Java 11 implementation under the normal output and Java 21 replacements under `META-INF/versions/21`.
   Set `Multi-Release: true`; otherwise the versioned entries are inert resources.
   Keep identical fully qualified names and compatible public signatures across base and versioned classes.
   Run tests against the packaged JAR on both 11 and 21; classpath tests against `target/classes` miss selection behavior.
   Prefer reflection or a tiny service-provider boundary when only one optimization needs a newer API.

6. **Separate language, library, and VM compatibility because each fails with a different symptom and needs a different gate.**
   Records fail Java 11 compilation; `Stream.toList()` can compile under bad flags and fail with `NoSuchMethodError`.
   Class files above 55 fail on Java 11 with `UnsupportedClassVersionError` before application code runs.
   Changed TLS, charset, provider, timing, or GC behavior appears only under execution on the old VM.
   Require compiler `release`, API signature checking, and real-runtime tests; none substitutes for another.

## Java 11-safe idioms

### Compatibility matrix

| Feature or API | Java 11 status | Java 11-safe choice |
|---|---|---|
| `List.of`, `Set.of`, `Map.of` | Available since 9 | Use for small unmodifiable collections; reject nulls and mutation |
| `Arrays.asList` | Available | Fixed-size, array-backed, permits null; wrap in `new ArrayList<>(...)` for mutation |
| Local-variable `var` | Available since 10 | Use only when the initializer makes the type obvious |
| Records | Not available | Final class, final fields, constructor validation, accessors, `equals`, `hashCode`, `toString` |
| Sealed classes/interfaces | Not available | Package-private constructors plus controlled implementations, or visitor interfaces |
| Pattern matching for `instanceof`/`switch` | Not available | Classic `instanceof`, cast, and explicit dispatch |
| Text blocks | Not available | Concatenated string literals or resource files |
| `Stream.toList()` | Not available; added in 16 | `collect(Collectors.toList())` or explicit unmodifiable collector |
| `Optional.isEmpty()` | Available since 11 | Use directly; `!isPresent()` is needed only below 11 |
| Switch expressions | Not available | Statement `switch` with assigned local and explicit `break` |
| Virtual threads | Not available; final in 21 | Bounded platform-thread executors and asynchronous I/O where justified |

### Rules

7. **Choose collection factories by mutability and null semantics because `List.of` and `Arrays.asList` are not interchangeable conveniences.**
   `List.of("a", "b")` is unmodifiable and throws `NullPointerException` for null elements.
   `Arrays.asList(array)` is fixed-size, writes through to the array, and throws on `add` or `remove`.
   Use `new ArrayList<>(Arrays.asList(...))` for a mutable independent list.
   Use `Collections.unmodifiableList(new ArrayList<>(input))` for a Java 11 defensive immutable snapshot.

8. **Use `var` only when it preserves local readability because Java 11 supports inference but not hidden domain meaning.**
   Prefer `var response = client.execute(request)` when the method name and initializer expose the type.
   Spell out types for numeric widening, overloaded factories, empty collections, and unfamiliar generic results.
   Never infer fields, parameters, or return types; Java does not permit it there.
   Do not confuse `var` availability with records, pattern variables, or later language features.

9. **Replace records with explicit value classes because record class-file and superclass semantics cannot be backported by `--release`.**
   Make the class `final`, fields `private final`, and validate invariants in the constructor.
   Implement accessors and value-based `equals`, `hashCode`, and `toString` deliberately.
   Copy mutable constructor inputs and return immutable views or copies.
   Generate boilerplate in the IDE or build; do not add runtime reflection merely to imitate record syntax.

10. **Replace sealed hierarchies and pattern matching with explicit closed-world dispatch because Java 11 cannot parse or enforce those constructs.**
    Keep implementations package-private and expose static factories when the implementation set must be controlled.
    Use a visitor when exhaustive behavior belongs outside variants; add a test covering every registered variant.
    Write `if (value instanceof Order) { Order order = (Order) value; }` rather than pattern variables.
    Use an enum discriminator when serialization requires a stable, explicit variant name.

11. **Replace text blocks and newer convenience APIs explicitly because syntax and API failures surface at different build stages.**
    Store long SQL, JSON, and templates in UTF-8 resources when indentation or escaping matters.
    Use adjacent concatenated literals for short strings; the compiler folds constants.
    Replace `stream.toList()` with `stream.collect(Collectors.toList())`, which returns a mutable list today.
    Use `Collectors.collectingAndThen(Collectors.toList(), Collections::unmodifiableList)` when immutability is contractual.
    Keep `Optional.isEmpty()`; it is part of the Java 11 API.

## Collections and streams

### Rules

12. **Prefer a loop in hot or branch-heavy code because stream setup, lambdas, iterator state, and intermediate objects can exceed the work per element.**
    Suspect streams for collections below roughly tens of elements inside millions of calls, not by collection size alone.
    Loops often win when they short-circuit irregularly, update several accumulators, or require indexed access.
    Streams often win in clarity for bulk transformations whose allocation and latency are outside hot paths.
    Decide with JMH and allocation profiles; source-code length is not a performance measurement.

13. **Supply a deliberate merge function to `Collectors.toMap` because duplicate keys otherwise throw `IllegalStateException` in production data.**
    Use `(left, right) -> left` only when first-wins is a documented ordering rule.
    Use `(left, right) -> right` only when encounter order is stable and last-wins is intended.
    Aggregate duplicates with `groupingBy` when losing a value would conceal invalid or meaningful multiplicity.
    Pass `LinkedHashMap::new` when downstream behavior requires encounter order; default `HashMap` promises none.

14. **Avoid nested `flatMap` in measured hot paths because each nested stream adds traversal machinery and can create many short-lived objects.**
    A loop with pre-sized output is clearer when flattening known collection sizes.
    `mapMulti` is not Java 11; do not adopt it in baseline code even though it can reduce stream creation on newer JDKs.
    Filter before flattening when the outer predicate can discard entire child collections.
    Profile allocation rate as well as wall time; GC pressure may be the dominant cost.

15. **Use primitive streams or primitive loops because `Stream<Integer>` allocates or reuses wrappers and performs unboxing at arithmetic boundaries.**
    Prefer `IntStream`, `LongStream`, and `DoubleStream` for numeric reductions.
    Use `mapToInt(Foo::size).sum()` rather than `map(Foo::size).reduce(0, Integer::sum)`.
    Primitive streams still have pipeline overhead; arrays and loops usually dominate the tightest numeric kernels.
    Watch maps and collectors too: standard generic collections box primitive keys and values.

16. **Pre-size concrete collections when cardinality is known because repeated growth copies arrays or rehashes buckets.**
    Use `new ArrayList<>(expectedSize)` for materialized one-to-one transformations.
    Size `HashMap` for load factor when evidence warrants it; avoid clever formulas unless large maps dominate allocation.
    Do not pre-size from untrusted counts without a cap; hostile lengths can turn a hint into memory exhaustion.
    Never expose the chosen mutable implementation as part of the API contract.

## Concurrency

### Rules

17. **Compose `CompletableFuture` stages by dependency shape because blocking with `join` inside a stage can deadlock a bounded executor and erase concurrency.**
    Use `thenApply` for synchronous transformation and `thenCompose` for a function returning another future.
    Use `thenCombine` for independent futures whose results meet; use `allOf` for a dynamically sized group.
    Attach `whenComplete` for observation and `handle` or `exceptionally` only when recovery is semantically valid.
    Apply timeouts and cancellation at request boundaries; cancellation does not reliably interrupt every underlying task.

18. **Pass an owned executor to asynchronous stages because the common fork-join pool is shared with unrelated work and tuned for CPU-bound tasks.**
    Size CPU pools near available processors, then measure under container CPU quotas.
    Size blocking pools from concurrency limits and downstream capacity, not from desired throughput alone.
    Bound queues and define rejection behavior so overload becomes visible instead of consuming all heap.
    Close executors during lifecycle shutdown and wait for termination with a finite deadline.

19. **Remove `ThreadLocal` values in `finally` because pooled threads outlive requests and retain both stale identity and referenced object graphs.**
    Use `try { context.set(value); work(); } finally { context.remove(); }` at the ownership boundary.
    A request that forgets cleanup can leak tenant credentials into the next request on the same worker.
    Large values remain reachable for the pool's lifetime and appear as unexplained retained heap.
    Prefer explicit context parameters when call depth and framework boundaries permit them.

20. **Treat virtual threads as a Java 21 deployment optimization because Java 11 has neither their API nor their scheduler behavior.**
    Keep baseline source free of `Thread.ofVirtual()` and `Executors.newVirtualThreadPerTaskExecutor()`.
    On Java 11, use bounded platform-thread pools, nonblocking clients, and downstream concurrency limits.
    Isolate a Java 21 implementation behind reflection, a service provider, or a multi-release JAR when the gain is measured.
    Virtual threads improve blocking-task scalability; they do not make CPU work faster or remove database limits.
    Avoid long synchronized/native blocking regions on virtual-thread paths; pinning can reduce carrier availability.

21. **Define interruption and timeout ownership because swallowed interrupts and unbounded waits prevent reliable cancellation and shutdown.**
    Restore status with `Thread.currentThread().interrupt()` when translating `InterruptedException` without rethrowing it.
    Put deadlines on network calls, queue offers, locks, and future joins; one outer HTTP timeout is insufficient.
    Distinguish timeout, cancellation, rejection, and business failure in metrics and exception types.
    Do not retry after interruption unless the caller's contract explicitly starts new work.

## Equality, hashing, and immutability

### Rules

22. **Implement `equals` and `hashCode` from the same stable state because equal objects must have equal hashes for hash-based collections to remain searchable.**
    `equals` must be reflexive, symmetric, transitive, consistent, and false for null.
    Use `getClass()` for strict value types; use `instanceof` only when cross-subclass equality is designed symmetrically.
    Include exactly the fields used by `equals` in `hashCode`; cache the hash only for deeply immutable objects.
    Never mutate equality fields while an object is a `HashMap` key or `HashSet` member.

23. **Separate entity identity from value equality because generated all-field equality changes as persisted entities acquire mutable state.**
    Prefer stable assigned identifiers for entities; database-generated IDs need an explicit pre-persistence policy.
    Do not mix business-key equality in one subclass with ID equality in another.
    Test symmetry against proxies when an ORM creates subclasses.
    Keep value objects immutable and compare all semantic components.

24. **Make defensive copies at both input and output boundaries because a final reference does not make its referenced object immutable.**
    Copy lists in constructors with `Collections.unmodifiableList(new ArrayList<>(input))` on Java 11.
    Copy arrays with `Arrays.copyOf`; clone mutable date-like legacy values on ingress and egress.
    Prefer `java.time` types because they are immutable and available in Java 11.
    Returning an unmodifiable view of a privately mutable list still reveals later internal mutations.

## Error handling and resources

### Rules

25. **Design exceptions around caller decisions because a type hierarchy is useful only when callers can recover, translate, retry, or abort differently.**
    Use checked exceptions for recoverable conditions a direct caller can reasonably handle; use unchecked exceptions for violated contracts and programming faults.
    Preserve stable machine-readable fields such as error code and resource ID instead of parsing messages.
    Keep messages actionable and free of credentials, tokens, personal data, and full request bodies.
    Do not declare `throws Exception`; it erases the recovery contract.

26. **Wrap an exception only when crossing an abstraction boundary because redundant wrapping obscures the useful stack and creates meaningless exception taxonomies.**
    Preserve the cause with `new RepositoryException("loading order " + id, cause)`.
    Translate vendor exceptions at the adapter boundary, not at every call frame.
    Preserve retry-relevant facts such as status code, timeout, and idempotency state.
    Avoid logging and rethrowing at each layer; log once where ownership and request context are known.

27. **Never swallow failures because an empty catch converts a diagnosable fault into corrupted state or misleading success.**
    Recover only by producing a valid fallback, retrying under policy, or returning an explicit failure.
    If cleanup failure is nonfatal, record it with enough identity to repair and expose a metric.
    Do not catch `Throwable`; `VirtualMachineError` and other fatal conditions are not application recovery signals.
    Preserve interrupts rather than treating them as routine errors.

28. **Use try-with-resources in acquisition order because it closes resources in reverse order and preserves close failures as suppressed exceptions.**
    Declare each `AutoCloseable` in the resource header; Java 11 permits an effectively final existing variable.
    The body exception is primary; exceptions from `close()` appear in `getSuppressed()`.
    Inspect suppressed exceptions during diagnosis when cleanup or commit protocols can fail.
    Avoid return statements from `finally`; they can discard the real failure.

```java
import java.io.BufferedReader;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

final class FirstLine {
    static String read(Path path) throws IOException {
        try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
            return reader.readLine();
        }
    }
}
```

## Maven build hygiene

### Rules

29. **Centralize versions in `dependencyManagement` because it controls transitive version selection without falsely adding dependencies to every module.**
    Import one reviewed BOM per platform family and pin exceptions with comments explaining the compatibility constraint.
    Declare direct dependencies in each consuming module; management alone does not place a JAR on its classpath.
    Run `mvn dependency:tree -Dverbose` when mediation selects an unexpected version.
    Keep plugin versions in `pluginManagement`; plugins do not use dependency management semantics.

30. **Enforce dependency convergence because nearest-wins mediation can compile against one API and execute with an incompatible transitive version.**
    Enable Maven Enforcer's `dependencyConvergence` and `requireUpperBoundDeps` where the ecosystem permits both.
    Resolve conflicts by upgrading the owning library, importing its BOM, or excluding one known transitive edge.
    Do not scatter exclusions until the tree is green; each exclusion transfers runtime responsibility to the application.
    Test the packaged artifact because IDE classpaths can differ from Maven resolution.

31. **Relocate shaded dependencies when isolation is required because copying classes without package relocation leaves duplicate definitions and classpath-order behavior.**
    Shading builds an aggregate artifact; relocation rewrites package references into a private namespace.
    Relocate embedded implementation libraries that may collide with host applications or plugin containers.
    Merge service descriptors with `ServicesResourceTransformer` when providers use `ServiceLoader`.
    Avoid exposing relocated types in public APIs; consumers cannot name a private implementation namespace safely.

32. **Make builds reproducible because timestamps, file order, generated metadata, and floating versions otherwise change artifacts without source changes.**
    Set `project.build.outputTimestamp` to a stable value or `SOURCE_DATE_EPOCH`-derived property.
    Pin every build plugin and ban version ranges, `LATEST`, and unreviewed snapshots in release branches.
    Compare checksums from two clean builds in isolated directories.
    Record the Maven and JDK versions used to publish while keeping output compatible with release 11.

33. **Fail early with Enforcer rules because discovering environment drift after packaging wastes CI time and can publish unsupported artifacts.**
    Require a Maven version, require the build JDK range, ban duplicate classes where practical, and ban forbidden dependencies.
    Enforce release-property presence in parent POMs shared by all modules.
    Keep skips opt-in, named, and disabled in CI; a silent `-Denforcer.skip` destroys the contract.
    Pair policy rules with runtime matrix tests rather than mistaking metadata for execution proof.

### Baseline build gate

This fragment compiles with a JDK 21+ Maven process, emits Java 11-compatible output, forks tests on a
real JDK 11 selected from `~/.m2/toolchains.xml`, and rejects references outside the Java 11 API:

```xml
<properties>
  <maven.compiler.release>11</maven.compiler.release>
  <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
</properties>
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-compiler-plugin</artifactId>
      <version>3.13.0</version>
      <configuration>
        <release>${maven.compiler.release}</release>
      </configuration>
    </plugin>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-surefire-plugin</artifactId>
      <version>3.5.2</version>
      <configuration>
        <jdkToolchain>
          <version>11</version>
        </jdkToolchain>
      </configuration>
    </plugin>
    <plugin>
      <groupId>org.codehaus.mojo</groupId>
      <artifactId>animal-sniffer-maven-plugin</artifactId>
      <version>1.24</version>
      <executions>
        <execution>
          <id>check-java-11-api</id>
          <phase>verify</phase>
          <goals><goal>check</goal></goals>
          <configuration>
            <signature>
              <groupId>org.codehaus.mojo.signature</groupId>
              <artifactId>java11</artifactId>
              <version>1.0</version>
            </signature>
          </configuration>
        </execution>
      </executions>
    </plugin>
  </plugins>
</build>
```

The toolchain entry must identify a real JDK 11 installation:

```xml
<?xml version="1.0" encoding="UTF-8"?>
<toolchains>
  <toolchain>
    <type>jdk</type>
    <provides><version>11</version></provides>
    <configuration><jdkHome>/opt/jdks/temurin-11</jdkHome></configuration>
  </toolchain>
</toolchains>
```

Run `mvn -V clean verify`; confirm the Surefire fork reports Java 11 in test diagnostics.

## Performance

### Rules

34. **Benchmark with JMH because ad hoc timers measure warmup, dead-code elimination, clock noise, and harness mistakes as if they were application work.**
    Use multiple forks, warmup iterations, measurement iterations, and representative parameter sizes.
    Consume results with `Blackhole` or return them; create state at the correct `@State` scope.
    Never run benchmarks in an IDE debug session or alongside noisy workloads.
    Report distribution and error bars, JDK build, JVM flags, CPU, power mode, and container limits.

35. **Profile allocation before rewriting code because throughput loss often comes from object churn and garbage collection rather than instruction count.**
    Use JFR allocation events for production-like runs and JMH `-prof gc` for microbenchmarks.
    Inspect bytes per operation, allocation rate, pause time, and retained heap separately.
    A high allocation rate with low retention suggests churn; high retained size suggests ownership or leaks.
    Validate on Java 11 and the newer deployment JDK because collectors and optimizers differ.

36. **Assume escape analysis may erase short-lived objects because the JIT can scalar-replace allocations that do not escape the compiled method graph.**
    Replacing a tiny value object with parallel primitives may produce identical machine code after warmup.
    Logging, reflection, volatile publication, polymorphism, and returning the object can prevent elimination.
    Confirm with allocation profiles and compiler diagnostics instead of reasoning from bytecode alone.
    Preserve clarity when the measured difference is within benchmark error.

37. **Optimize the dominant production path because micro-optimizations disappear behind I/O, cache misses, contention, or a different JIT compilation decision.**
    Start with end-to-end latency profiles and service-level percentiles, then isolate the hottest method.
    Test realistic data distributions; uniform toy inputs hide branch behavior and hash collisions.
    Re-run after dependency or JDK upgrades because inlining and intrinsic choices change.
    Keep a regression benchmark only when its variance is low enough to detect the claimed gain.

## Common pitfalls

1. **Reject `source=11,target=11` on a newer JDK because it can compile newer API calls into bytecode that Java 11 cannot link.**
   Symptom: CI compiles successfully, then Java 11 throws `NoSuchMethodError` for `Stream.toList`.
   Fix: use `release=11`, add Animal Sniffer, and run the test suite on JDK 11.

2. **Reject class files above version 55 because Java 11 cannot load bytecode emitted for later releases.**
   Symptom: startup fails with `UnsupportedClassVersionError` naming class-file version 61 or 65.
   Fix: inspect every module and generated source path; enforce compiler release and dependency runtime baselines.

3. **Reject newer syntax in baseline sources because the Java 11 compiler cannot parse records, sealed types, pattern matching, text blocks, or switch expressions.**
   Symptom: compilation fails near `record`, `sealed`, `"""`, `->`, or an `instanceof` binding variable.
   Fix: use explicit Java 11 equivalents or isolate newer code in a correctly packaged multi-release layer.

4. **Define duplicate-key behavior before collecting maps because `Collectors.toMap` defaults to throwing on the first collision.**
   Symptom: an intermittent `IllegalStateException: Duplicate key` appears only with production-shaped data.
   Fix: validate uniqueness, aggregate with `groupingBy`, or supply a documented merge function.

5. **Keep mutable equality state out of hash keys because bucket placement is not recomputed after mutation.**
   Symptom: `contains` and `remove` return false for the exact object already present in a `HashSet`.
   Fix: use immutable value keys or stable identifiers and rebuild corrupted collections.

6. **Clean thread-local context at request completion because pooled workers reuse values and retain referenced graphs.**
   Symptom: one tenant sees another tenant's context, or heap analysis shows request objects retained by executor threads.
   Fix: call `remove()` in `finally` at the boundary that sets the value.

7. **Avoid blocking a future on its own bounded executor because all workers can wait while queued continuations have no thread.**
   Symptom: CPU is idle, queue depth grows, and thread dumps show workers blocked in `join` or `get`.
   Fix: compose with `thenCompose` or `thenCombine` and separate unavoidable blocking work.

8. **Preserve exception causes and suppressed failures because cleanup faults and vendor diagnostics otherwise disappear.**
   Symptom: logs contain only a generic wrapper or report success despite a failed close, rollback, or flush.
   Fix: pass the cause, use try-with-resources, and inspect `getSuppressed()` in diagnostics.

9. **Relocate embedded libraries when shading for isolation because duplicate packages remain subject to classpath order without relocation.**
   Symptom: `NoSuchMethodError`, `LinkageError`, or provider discovery differs between standalone and hosted execution.
   Fix: relocate private packages, merge service files, and test the final shaded JAR in the host.

10. **Verify the actual test JVM because Maven running on JDK 21 does not imply Surefire tested compatibility with Java 11.**
    Symptom: every compatibility job reports the same `java.runtime.version`, or the toolchain configuration is silently unused.
    Fix: assert feature version 11 in the baseline test profile and fail when the toolchain cannot resolve.

### Review checklist

- Verify every production module inherits `maven.compiler.release=11` and no module overrides `source` or `target`.
- Verify baseline CI executes packaged code and tests on a real JDK 11, while a newer-JDK lane also remains green.
- Verify Animal Sniffer checks Java 11 APIs and japicmp guards published library compatibility.
